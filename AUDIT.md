# Аудит AquaControl Pro — 17.08.2026

Версия на момент аудита: **1.0.28 (build 29)**, коммит `8522e4a`.
Проверено: `index.html` (1689 строк), `.github/workflows/build.yml`, `manifest.json`, `PROJECT.md`, `README.md`.
Приложение работает, критических падений не найдено. JS проходит синтаксическую проверку,
все функции, вызываемые из `onclick`, существуют.

Ниже — честный разбор. Обозначения приоритетов:

- **P0** — блокирует массовый запуск или публикацию в магазине;
- **P1** — сильно мешает обычному пользователю;
- **P2** — улучшение, можно отложить.

---

## 1. Что сделано хорошо (это не надо трогать)

1. Одна страница, ноль сервера, ноль регистрации — данные пользователя физически не покидают телефон.
   Это сильная и честная позиция, её надо вынести в описание магазина.
2. Экспорт резервной копии через системное окно Android (SAF) без лишних плагинов — грамотное решение.
3. Экран «Настроить уведомления» с проверкой реально выданных разрешений и подсказками по прошивкам
   (Xiaomi, Huawei, Oppo, Vivo, Samsung) — этого нет у большинства конкурентов.
4. Стабильная подпись APK через секрет репозитория — обновления «поверх» работают.
5. Расписание уведомлений строится через очередь промисов (`scheduleChain`), с повторной проверкой
   `getPending()` — защита от гонок сделана осознанно.
6. Подсказки «?» с человеческим языком.

## 2. P0 — блокирует магазин и массовый запуск

### 2.1. Сборка отладочная, а не релизная

`build.yml` собирает `assembleDebug`. Это значит в APK `android:debuggable="true"`.

Последствия:

- модерация RuStore (антивирусная проверка «Лаборатории Касперского» + ручная) с высокой вероятностью
  отклонит такую сборку;
- любой человек с USB-отладкой может вытащить данные приложения с телефона пользователя;
- сборка тяжелее и медленнее.

**Решение:** релизная сборка `assembleRelease`, подписанная **тем же самым ключом**,
что и сейчас (секрет `DEBUG_KEYSTORE_BASE64`). Ключ у вас нестандартный (CN=AquaControlPro),
это полноценный ключ на 30 лет — менять его не нужно и **не желательно**:
сохранив его, вы сохраните возможность обновления поверх уже установленного приложения.

Готовый workflow: `.github/workflows/release.yml` (ручной запуск, старый `build.yml` не тронут).

### 2.2. Приложение при первом запуске выбрасывает в системные настройки — исправлено в 1.0.29

> Решение по итогам обсуждения с владельцем: системные окна убраны из автозапуска,
> но вместо них на первом запуске показывается экран-объяснение «зачем нужны три
> разрешения», а на главном экране постоянно висит полоса-предупреждение, пока
> напоминания не смогут приходить. Пользователю не нужно догадываться самому.

`MainActivity.onCreate` сразу вызывает `requestExactAlarmPermission()` и
`requestIgnoreBatteryOptimizations()`. Пользователь, впервые открывший приложение, видит
не приложение, а два системных экрана Android подряд.

Для одного своего телефона это удобно. Для массового пользователя это:

- худший возможный первый экран (часть людей просто удалит приложение);
- красный флаг для модерации: «избыточные разрешения без объяснения» — типовая причина отказа.

**Решение:** убрать авто-вызовы из `onCreate`. Разрешения запрашивать только из уже существующего
экрана «Настроить уведомления», по нажатию кнопки, после объяснения — там всё это уже реализовано.

### 2.3. Нет политики конфиденциальности

Обязательна для RuStore: публичный URL + ссылка внутри приложения.
Подготовлено: `PRIVACY.md` (текст) и `privacy.html` (страница для GitHub Pages).
Публичный адрес после слияния в `main`:
`https://help-yourself-dvp.github.io/water-filter/privacy.html`

### 2.3-бис. Иконка приложения — чужой сток с водяными знаками (нашлось при аудите)

Файл `icon.png` (1024×1024) — это картинка с фотостока **PNGTree**, и на ней по диагонали
повторяется полупрозрачная надпись «pngtree». Она видна и в самом файле, и в иконке
на телефоне (при уменьшении читается как грязь/шум).

Это сразу две проблемы:

- **юридическая:** использование стокового изображения без лицензии. RuStore при модерации
  проверяет права на контент, а водяной знак — прямое доказательство отсутствия лицензии.
  Такая карточка отклоняется, а в тяжёлом случае это претензия правообладателя;
- **качественная:** иконка — первое, что видит человек в магазине.

**Решение:** заменить на собственную иконку. Подготовлены два варианта:
`store/icon-proposal-a-1024.png` (капля в кольце прогресса) и
`store/icon-proposal-b-1024.png` (капля с минималистичным циферблатом).
После выбора я заменю `icon.png` — иконки Android генерируются из него автоматически при сборке.
Файл 512×512 для карточки магазина я сделаю сразу после вашего выбора — из старой иконки
его готовить нельзя по той же причине.

### 2.4. Нет экрана «О приложении» и контакта поддержки

Магазин требует контакты разработчика; пользователю нужно куда-то написать об ошибке.
Сейчас в приложении есть только строка с версией.

**Решение:** раздел «О приложении» в «Настройках»: версия и номер сборки, ссылка на политику
конфиденциальности, email поддержки, «Что нового», строка «Все данные хранятся только на вашем телефоне».

### 2.5. Демо-данные вместо первого запуска

Новый пользователь получает готовые «Моя квартира», «Дом родителей» и фильтр «Кувшин Кухня»
с брендом «Аквафор» и датой замены = момент установки. Он вынужден догадаться, что это чужие
выдуманные данные, отредактировать их или удалить.

**Решение:** короткий первый запуск на 3 экрана: «Как назвать объект?» → «Какой фильтр?»
(тип + срок) → «Когда меняли в последний раз?» (сегодня / выбрать дату). После этого сразу
рабочий экран с честным счётчиком. Демо-данные создавать только по кнопке «Показать пример».

### 2.6. Нельзя указать реальную дату последней замены — исправлено в 1.0.29

`lastDate` всегда `Date.now()` — и при создании фильтра, и при фиксации замены.
Человек, который поставил картридж месяц назад, не может это ввести: счётчик врёт на месяц.
Для приложения, вся ценность которого в правильной дате, это ключевой дефект.

**Решение:** поле выбора даты (`<input type="date">`) при создании фильтра и при фиксации замены,
по умолчанию — сегодня.

## 3. P1 — сильно мешает обычному пользователю

### 3.1. Тестовые режимы видны всем — исправлено в 1.0.29

В «Новый фильтр» и «Изменить фильтр» первыми стоят оранжевые чипы «1 мин (тест)», «5 мин (тест)»,
«1 час (тест)». Обычный человек не понимает, что это, а нажав — получает вечно «просроченный» фильтр
и уведомления каждую минуту.

**Решение:** убрать из релиза, оставив скрытый вход (например, 7 нажатий на строку с версией
включает «режим разработчика»).

### 3.2. Время уведомления не выбирается — исправлено в 1.0.29

Уведомление планируется на **точный момент истечения срока** — то есть на то же время суток,
когда фильтр был создан. Замена в 23:40 → напоминание в 23:40, возможно ночью.

**Решение:** планировать на выбранный час (по умолчанию 10:00 утра); в настройках — «Время напоминаний».

### 3.3. Нет предупреждения заранее — исправлено в 1.0.29

Сейчас два уведомления: в момент истечения и через 7 дней. Но картридж надо **купить заранее**.

**Решение:** третье уведомление «за N дней» (по умолчанию 7) с кнопкой перехода в магазин по сохранённой ссылке.

### 3.4. Нажатие на уведомление портит данные — исправлено в 1.0.29

В обработчике `localNotificationActionPerformed`:

```js
if (t.leftMs > 0) f.lastDate = Date.now() - (t.resourceMs + 5000);
```

То есть если пользователь откроет старое уведомление по фильтру, который он уже заменил,
приложение **принудительно сделает фильтр просроченным**. Это молчаливая порча данных.

**Решение:** убрать эту строку. Открывать нужный фильтр и показывать окно замены — этого достаточно.

### 3.5. История общая, без привязки к дому и фильтру

В `history` пишется только `filterName`, `date` (строкой), `cost`, `note`. При двух домах
с фильтрами «Кувшин» в каждом записи неразличимы. Нельзя отфильтровать историю по дому,
нельзя удалить или исправить ошибочную запись, дата хранится как локализованная строка,
а не как число — по ней невозможно ни сортировать, ни считать средний интервал.

**Решение:** добавить в запись `locationId`, `filterId`, `ts` (число). Старые записи не трогать
(миграция «если нет ts — считать по date»). Добавить удаление записи долгим нажатием.

### 3.6. Сомнительные цифры экономии

`n * 200` бутылок и `n * 9000 ₽` за каждую замену — независимо от типа фильтра и цены.
Для кувшина на 60 дней это завышено в разы. В подсказке честно написано «примерная оценка»,
но цифра в интерфейсе выглядит как факт, а в описании магазина такая цифра — риск претензии.

**Решение:** считать от реальных данных (объём ресурса × цена литра бутилированной воды)
или убрать рубли, оставив бутылки со сноской. В описании магазина цифру не использовать.

### 3.7. Срок службы — только 6 фиксированных вариантов

30 / 60 / 90 / 180 / 365 дней. Реальные картриджи бывают на 45 дней, 4 месяца, 2 года,
а системы обратного осмоса — набор из 3–5 ступеней с разными сроками (предфильтры 6 мес,
мембрана 2 года, постфильтр 1 год).

**Решение:** поле «свой срок, дней». Для осмоса — либо шаблон «создать 4 ступени одной кнопкой»,
либо честно описать в справке приём «каждая ступень = отдельный фильтр».

### 3.8. Пользовательский текст не экранируется — исправлено в 1.0.29

Названия домов, фильтров и брендов вставляются через `innerHTML` (вкладки, список домов, история).
Название вида `Кувшин <кухня>` частично исчезнет, а кавычка в названии дома сломает
`onclick="selectLocationDirect('...')"`. Это не «взлом» (данные свои), но интерфейс ломается.

**Решение:** функция `esc(s)` с заменой `& < > " '` и использование её во всех местах вставки.

### 3.9. Нет общей сводки

Главный экран показывает **один** фильтр. Пользователю с 2 домами и 5 фильтрами, чтобы понять
«что горит», надо переключить дом, потом каждую вкладку.

**Решение:** экран «Все фильтры»: список всех объектов и фильтров, отсортированный по остатку дней,
с цветными метками. Это самая полезная функция из недостающих.

### 3.10. Тип фильтра ни на что не влияет

`type` (Кувшин / Проточный / Осмос / Насадка) только отображается. При этом он мог бы задавать
разумный срок по умолчанию и текст подсказок. Плюс в «Изменить фильтр» тип вообще нельзя поменять.

## 4. P2 — улучшения второго круга

1. **Фон.** Анимация волн и частиц (`requestAnimationFrame`, 50 частиц) плюс `backdrop-filter: blur(30px)`
   работают постоянно, пока экран открыт. На слабых телефонах это заметный расход батареи и нагрев.
   Достаточно останавливать анимацию, когда открыто модальное окно и когда вкладка скрыта.
2. **Контраст.** Серый `#6e7d93` на почти чёрном фоне и подписи 11 px — на солнце и людям 50+ читается плохо.
3. **Только тёмная тема.** Светлая тема заявлена в планах, для массовой аудитории желательна.
4. **Только русский язык.** Для RuStore достаточно, для роста — нет.
5. **Нет виджета на рабочий стол** — для такого приложения это естественная функция, но требует нативной работы.
6. **Нет сброса всех данных** (кроме удаления приложения).
7. **manifest.json** объявляет иконку 512×512, а `icon.png` — 1024×1024; и `start_url: ./index.html`
   лучше заменить на `./`. Мелочь, но PWA-валидаторы ругаются.
8. **Свайп между домами** ловит любой горизонтальный жест по карточке; при одном доме подсказка скрыта, но
   обработчик всё равно висит.
9. **Нет ограничения на размер истории** — через годы список станет длинным (не страшно, но стоит помнить).
10. **iOS не поддерживается** — и не планируется; это нормально, но должно быть написано в документации.

## 5. Что лишнее (кандидаты на удаление)

1. **Тестовые чипы сроков** — в релизе лишние (см. 3.1).
2. **Разрешение `USE_EXACT_ALARM`.** Для напоминания о картридже точность до секунды не нужна.
   `SCHEDULE_EXACT_ALARM` пользователь может выдать сам, а `USE_EXACT_ALARM` — «безусловное» разрешение,
   которое магазины считают избыточным для не-будильников. Рекомендую убрать его из манифеста
   и оставить обычные (неточные) напоминания с окном в несколько часов: для срока в 90 дней это незаметно.
   **Спорно — решение за вами**, потому что часть прошивок задерживает неточные будильники на сутки.
3. **Экспорт «текстом в буфер обмена»** — запасной путь для старых сборок APK. Сейчас нативный мост есть
   всегда, ветку можно оставить (она безвредна), но в документации отметить как legacy.
4. **Два дублирующих AI-гайда** (`AI_GUIDE.md`, `AI_GUIDE (LifeFlow).md`) — почти идентичны.
   Заменены единым `AI_GUIDE_AQUACONTROL.md`; исходники оставлены как архив.

## 6. Версионность и обновление поверх — результат проверки

**Работает, но держится на честном слове.** Разбор по частям:

| Что | Как сейчас | Оценка |
|---|---|---|
| `versionCode` | `sed -i 's/versionCode 1/versionCode 29/g'` в `build.yml` | Работает, пока шаблон Capacitor содержит строку `versionCode 1`. Номер вбит вручную в трёх местах YAML + в `index.html` — легко забыть и выпустить две разные сборки с одним кодом. Android тогда откажется обновлять («приложение не установлено»). |
| `versionName` | `sed` по `versionName "1.0"` | То же самое. |
| Подпись | debug-keystore из секрета `DEBUG_KEYSTORE_BASE64` | Ключ стабильный — обновление поверх работает. **Но:** если секрет когда-нибудь пропадёт, workflow только напечатает предупреждение и соберёт APK со **случайным** ключом. Такой APK не встанет поверх, а пользователи получат «Приложение не установлено». Сборка обязана падать. |
| Проверка подписи | нет | Отпечаток сертификата нигде не проверяется. Опыт «Волшебной полянки»: AGP умеет молча подменить ключ. |
| Сохранность данных | `localStorage` в WebView | При обновлении поверх сохраняется. При удалении приложения — теряется. Резервная копия делается только вручную. |
| Имя файла APK | `AquaControlPro-v1.0.28-build29.apk`, вбито вручную | Расходится с реальной версией при забытом `sed`. |

**Что сделано в этом обновлении:**

- добавлен `version.json` — единственный источник версии;
- добавлен `.github/workflows/release.yml`: версии берутся из `version.json`, сборка **release**,
  подпись прописывается явно в Gradle, отпечаток сертификата печатается в лог,
  отсутствие ключа = падение сборки, проверка совпадения версии в `index.html`,
  проверка `debuggable`, автоматическая публикация в GitHub Release;
- старый `build.yml` намеренно **не изменён** (правило: инфраструктуру меняем минимально
  и проверяем по шагам). Он остаётся для отладочных сборок.
