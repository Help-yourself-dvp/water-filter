# AI Guide — AquaControl Pro

Единый рабочий гайд проекта AquaControl Pro.

Собран из трёх исходных документов, которые лежат в репозитории:

| Файл | Что это | Что взято сюда |
|---|---|---|
| `AI_GUIDE.md` | универсальный гайд владельца (версия AquaControl) | базовые правила общения, работа с кодом, версии, безопасность данных |
| `AI_GUIDE (LifeFlow).md` | тот же универсальный гайд из проекта LifeFlow, немного причёсанный | формулировки-уточнения, ничего нового по смыслу |
| `AI_GUIDE_(WONDERMEADOW).md` | гайд проекта «Волшебная полянка» — самый развитый | экономия контекста диалога, подпись APK, релизный процесс, требования магазина, метод «Совет участников», проверка сборки |

**Этот файл — главный для AquaControl Pro.** Три исходных гайда остаются в репозитории
как архив и источник опыта, но при работе над AquaControl приоритет у этого документа.

Прикладывать к новому диалогу: `AI_GUIDE_AQUACONTROL.md` + `PROJECT.md` + `index.html` + описание одной задачи.

## 1. Основной принцип

Максимально быстро получить стабильный рабочий результат.
Работающее приложение важнее идеального кода.
Каждое изменение делает проект лучше, но не увеличивает сложность без необходимости.

## 2. Уровень владельца и стиль ответов

- Владелец не программист. Не предполагается знание Android SDK, Java, Kotlin, Gradle, YAML, Git, GitHub Actions.
- **Владелец читает ответы с телефона.** Ответ = пронумерованные шаги + полные кликабельные ссылки.
- **Ловушка со ссылками (проверено на этом проекте):** имя рабочей ветки содержит косую черту
  (`arena/01a00e70-water-filter`), и GitHub не всегда понимает, где кончается ветка и начинается
  путь к файлу — страница открывается с ошибкой «Error loading page».
  Ссылки на файлы давать **по SHA коммита**:
  `https://github.com/<owner>/<repo>/blob/<полный-sha>/<путь>`.
- **Ещё важнее (проверено 17.08.2026): у владельца страницы GitHub открываются нестабильно** —
  бывают ответы «No server is currently available» и «Error loading page» даже при переходе
  руками по репозиторию. Причина вне проекта (сеть/провайдер/мобильный интернет).
  Вывод для любого проекта: **нельзя делать GitHub единственным способом прочитать инструкцию.**
  Порядок такой:
  1. Краткие шаги — прямо в ответе в чате, без ссылок.
  2. Полная инструкция — PDF в просмотрщике Arena (`tools/md_to_pdf.py` делает PDF
     из любого нашего .md за секунду), PDF открывается без сети.
  3. Ссылка на GitHub — только как дополнительный вариант, не основной.
- **Файлы от владельца принимать вложением в чат**, а не через загрузку в репозиторий:
  если GitHub у него не открывается, загрузить туда файлы он тоже не сможет.
- **Первым делом при странных ошибках GitHub — проверить, живой ли сам GitHub**, а не искать
  ошибку в проекте. Быстрая проверка без входа в аккаунт:
  `https://www.githubstatus.com/api/v2/summary.json` — в конце ответа поле `status.indicator`
  (`none` = всё в порядке) и список компонентов со статусами
  (`operational` / `degraded_performance` / `major_outage`).
  Человеку — страница https://www.githubstatus.com и https://сбой.рф.
  Проверено 17.08.2026: жалобы владельца «Error loading page» и «No server is currently
  available» совпали с критическим инцидентом GitHub (около 20% ошибок веб-страниц
  и до 50% ошибок при скачивании файлов из репозиториев). Проект был ни при чём.
- **Во время инцидента не запускать сборки и не сливать ветки:** Actions в такие моменты
  падают на ровном месте, и легко принять сбой инфраструктуры за поломку кода.
  Правильное поведение — приостановиться, сообщить владельцу причину и вернуться позже.
- Меньше обсуждений — больше готовых решений: краткое объяснение → шаги → готовый код/текст.
- Не присылать простыни кода в чат. В чат — только изменяемый блок; полные файлы живут в репозитории.
- Мелкие технические решения (имена функций, расположение кода, оформление) AI принимает сам.
  Согласование обязательно, если меняются: функциональность, архитектура, безопасность данных, совместимость версий, подпись APK.

## 4. Экономия контекста диалога (правило навсегда)

Длинный диалог замедляется и упирается в лимиты. Поэтому:

1. **Не читать `index.html` целиком** (1700 строк). Искать `grep -n` и читать нужные диапазоны `sed -n 'N,Mp'`.
2. Правки — точечные (`edit_file`), не перезапись всего файла.
3. В ответах — только изменяемый блок, без длинных диффов.
4. Минимизировать вывод команд (`| tail`, `grep`, `head`).
5. Скриншоты — по необходимости; для рутинной проверки хватает программных сигналов
   (синтаксис JS, наличие ID, отсутствие ошибок консоли).
6. Итоги спринта фиксировать в документах (`PROJECT.md`, `CHANGELOG.md`), чтобы следующий диалог
   стартовал с чистого контекста.
7. Перед сменой диалога оставлять короткую передачу: SHA, версия, изменённые файлы, ссылки на CI/Release.

## 4а. Визуальный стиль — не менять без решения владельца

Стиль приложения: **неон на тёмном фоне**, идея от заставки PlayStation — тёмный фон,
живая анимация волн и пузырьков, светящийся бирюзовый акцент `#00F2FE`.

- Это самостоятельный фирменный вид, а не «тёмная тема» из пары день/ночь.
- С версии 1.0.35 есть второй вариант — **светлое оформление**, выбирается вручную
  в настройках (`settings.theme`). Механика та же (волны, пузырьки), меняется палитра.
  Автоматическое переключение по системному режиму делать не нужно — так решил владелец.
- Анимированный фон — часть узнаваемости. Его можно оптимизировать (не рисовать, когда не видно),
  но не удалять.
- Проблемы читаемости решаются внутри стиля: светлее серый текст, крупнее мелкие надписи.
- **Никаких ссылок наружу в интерфейсе** (решение владельца): политика конфиденциальности,
  справка и «О приложении» открываются внутри приложения и работают без интернета.
  Единственная внешняя ссылка — магазин картриджей, который пользователь вписал сам.
- Любые «числа-обещания» (экономия, бутылки, литры) — **справочные**: считаются по данным
  пользователя, допущения заполнены средними значениями и подписаны прямо под цифрами.
  Приложение не превращается в калькулятор бюджета: расширять этот раздел запрещено.

## 5. Архитектура и зависимости

- Одностраничное приложение: **весь UI, CSS и логика — в `index.html`**. Не дробить на файлы без нужды.

- Данные — только на устройстве, `localStorage`, ключ `aquaControlProDB`. Сервера и регистрации нет.

## 6. Работа с кодом и версиями

- Одна версия = одна небольшая законченная задача. Не смешивать изменения в релизе.
- Малое изменение — заменять одну функцию / один HTML-блок / один CSS-блок, а не файл целиком.
- Не переписывать рабочий код без причины; максимально сохранять существующую архитектуру.
- Стабильность важнее новых функций. Приоритет работ:
  1) исправление ошибок → 2) стабильность → 3) удобство пользователя → 4) упрощение разработки →
  5) новый функционал → 6) косметика.

### Единый источник версии

Версия хранится в **`version.json`**:

```json
{ "versionName": "1.0.29", "versionCode": 30 }
```

Правила:

- `versionCode` **только растёт** на 1 при каждом выпуске. Android откажется ставить APK с меньшим или равным кодом.
- `versionName` — то, что видит пользователь.
- Номер версии дублируется в `index.html` (`id="appVersionTag"`). **Это ловушка из WONDERMEADOW:**
  хардкод-версии забывают обновить. Поэтому релизный workflow **падает**, если строка в `index.html`
  не совпадает с `version.json`. Обновлять оба места одновременно.

## 7. Подпись APK и обновление «поверх» (критично, не ломать)

- Подпись APK **должна оставаться постоянной навсегда**. Пользователь никогда не должен удалять приложение перед обновлением.
- Ключ лежит в секрете репозитория `DEBUG_KEYSTORE_BASE64` (base64 от `debug.keystore`,
  PKCS12, alias `androiddebugkey`, пароль `android`, срок 30 лет).
  Он сгенерирован workflow `generate-keystore.yml` и должен быть **скачан и сохранён владельцем вне GitHub**.
- **Потеря ключа = конец обновлениям.** Все пользователи будут обязаны удалить приложение и потерять данные.
  Хранить копию в двух местах (облако + офлайн).
- ⏰ **Напоминание владельцу (по его просьбе):** скачать копию ключа перед первой публикацией
  в магазине. AI обязан напомнить об этом на шаге подготовки релиза.
- Опыт WONDERMEADOW: недостаточно просто положить keystore в `~/.android/` — Android Gradle Plugin
  может молча сгенерировать случайный ключ. Ключ **явно прописывается** в `signingConfigs` в `android/app/build.gradle`.
- Контроль в CI: отпечаток сертификата SHA-256 печатается в лог и сравнивается с эталоном.
  Сравнивать **только fingerprint сертификата**, не хэш файла `META-INF/CERT.RSA` (там метка времени, он меняется всегда).
- Если секрет с ключом не найден — **сборка обязана падать**, а не выпускать APK со случайной подписью.

## 8. Релизный процесс (эталон для AquaControl)

1. Обновить `index.html` (одна задача), `version.json`, `CHANGELOG.md`.
2. Коммит в рабочую ветку → Pull Request → merge в `main`.
3. `build.yml` (push в `main`) собирает **отладочный APK** — только для собственной проверки на телефоне.
4. `release.yml` (ручной запуск, «Run workflow») собирает **релизный подписанный APK** для магазина.
   Важно: GitHub показывает кнопку «Run workflow» только для файлов, которые есть в ветке `main`,
   поэтому релизная сборка станет запускаемой после слияния рабочей ветки:
   - `versionName`/`versionCode` берутся из `version.json`;
   - проверяется совпадение версии в `index.html`;
   - проверяется `android:debuggable` = отсутствует/false;
   - печатается и сверяется отпечаток сертификата;
   - APK публикуется в GitHub Release с именем `AquaControlPro-<версия>-release.apk`.
5. Перед словом «готово» проверить: `conclusion=success`, версия в теге = `version.json`, Release публичный, размер файла ненулевой.
6. Логи Actions из песочницы Arena скачать нельзя (блокируется CDN). Поэтому проверки
   встроены в сам workflow: он сравнивает отпечаток сертификата APK с отпечатком ключа
   и падает при расхождении. Читать «зелёный/красный» через API достаточно.
7. Релизную сборку можно запускать из рабочей ветки, не сливая её в `main`:
   достаточно изменить файл `release.trigger`.
6. Установить APK поверх предыдущей версии на реальном телефоне и убедиться, что данные на месте.
7. Только после этого — загрузка в RuStore (см. `RUSTORE.md`).

## 9. Безопасность данных пользователя

- При обновлении данные обязаны сохраняться. Если есть риск потери — предупредить **заранее и явно**.
- Любое изменение структуры данных в `localStorage` требует миграции: новые поля добавляются
  с безопасным значением по умолчанию, старые не удаляются молча.
- Перед импортом резервной копии — автоматически делать копию текущих данных (в плане).
- Опасные действия (удаление объекта, импорт, сброс) — только через подтверждение.

## 10. Требования магазина (RuStore) — постоянный чеклист

Держать выполненным всегда, иначе релиз не пройдёт модерацию:

- APK **release-сборки**, подписан постоянным ключом, `debuggable=false`;
- `targetSdkVersion` не ниже 28 (у нас 34);
- уникальный `packageName` (`com.aquacontrol.pro`), в новых версиях `versionCode` растёт;
- политика конфиденциальности доступна по публичному URL **и** ссылкой внутри приложения;
- контакт поддержки (email) в карточке магазина и в приложении;
- запрашиваются только реально нужные разрешения, каждое объяснимо одной фразой;
- приложение не должно на первом запуске выбрасывать пользователя в системные настройки;
- иконка 512×512, минимум 4 скриншота, описание на русском (краткое ≤ 80 символов, полное ≤ 4000).

Подробности и готовые тексты — в `RUSTORE.md`.

## 10а. Скриншоты для магазина — процедура (кандидат в универсальный гайд)

**СТАТУС: обкатывается на AquaControl.** Если процедура пройдёт живой прогон
(снимки → сборка → загрузка → модерация) без замечаний, переносим её в общий
гайд владельца и в следующих проектах идём сразу по ней, ничего не выдумывая.

Порядок:

1. **Сначала данные, потом снимки.** В приложении делается скрытая (в режиме проверки)
   кнопка «Демо-данные для скриншотов»: набор, где видны все состояния сразу —
   норма, «скоро», просрочено, плюс история. Свои данные владелец перед этим
   сохраняет в резервную копию и возвращает после съёмки.
2. **Список кадров пишется заранее**, по одному экрану на смысл, и первые два —
   самые важные (их видит почти вся аудитория). Для AquaControl: главный счётчик →
   сводка «Все фильтры» → фиксация замены → настройка уведомлений → расходы →
   альтернативное оформление.
3. **Технический размер решается скриптом, а не обрезкой.** Магазин ждёт 16:9
   (1080×1920), телефон снимает 20:9. Скрипт `store/make_store_shots.py` вписывает
   кадр целиком в холст на фирменном фоне и добавляет короткую подпись.
   Ничего не обрезается, подписи читаются в миниатюре.
4. **Спор «светлые или тёмные» решается так:** скриншоты показывают приложение
   таким, какое оно есть (иначе — удаления после установки), а контраст в ленте
   магазина обеспечивает фирменный цветной фон вокруг кадра. Один кадр
   с альтернативным оформлением ставится в конец набора, не в начало.
5. **Проверка перед загрузкой:** уменьшить картинку до размера плитки каталога
   и посмотреть с расстояния вытянутой руки — читается ли подпись и главный элемент.
6. Правила магазина, которые легко нарушить по незнанию: нельзя показывать
   системный интерфейс Android и чужие приложения, нельзя показывать функции,
   которых нет, текст — на русском.

## 11. Метод «Совет участников» (из WONDERMEADOW, адаптирован)

Любой текст, который увидит пользователь (кнопки, подсказки, уведомления, описание в магазине),
прогоняется через четыре роли, вердикт каждой приводится коротко:

1. **Обычный пользователь 45+** — понятно с первого прочтения? нет ли технических слов
   («экспорт JSON», «Storage Access Framework»)?
2. **Скептик** — не обещаем ли лишнего (экономия «9000 ₽», «200 бутылок»)? можем ли доказать цифру?
3. **Модератор магазина** — нет ли обмана, медицинских обещаний («чистая вода полезна для здоровья»),
   чужих торговых марок в неверном контексте?
4. **Критик** — не выглядит ли текст из 2000-х? нет ли капса и восклицаний?

Спорные формулировки выносить владельцу как развилку.

## 12. Накопленный опыт проекта (не терять)

- Не добавлять Capacitor-плагины без реальной необходимости (1.0.22 — падение при запуске).
- Изменения инфраструктуры (`build.yml`, Gradle, подпись, Capacitor) — высокорисковые:
  менять минимально необходимый участок, после каждого изменения проверять сборку.
- Рабочий файл `build.yml` не переписывать целиком. Новый рискованный сценарий выносить в **отдельный**
  workflow, пока он не доказан (так сделан `release.yml`).
- Документация описывает только реально работающий функционал.
- После правок HTML/JS проверять: все функции из `onclick` существуют, все ID на месте,
  `querySelectorAll` — это NodeList, для `.some/.map/.filter` приводить через `Array.from()`.
  Быстрая проверка без телефона: вырезать `<script>` и прогнать `node --check`.
- Пользовательский текст (названия домов, фильтров, брендов) **экранировать** перед вставкой
  через `innerHTML`, иначе символы `<`, `>`, кавычки ломают вёрстку.
- Уведомления Android: точное время не гарантируется без разрешений; помощник настройки
  («Настроить уведомления») — обязательная часть продукта, а не украшение.
- Тестовые режимы (сроки в минутах) не должны быть видны обычному пользователю в релизе.

## 13. Что делать в начале нового диалога
